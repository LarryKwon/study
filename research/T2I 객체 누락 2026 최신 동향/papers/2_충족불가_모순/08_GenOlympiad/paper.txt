                                                      Text-to-image models have made tremendous progress and can produce high-
                                                      quality images. However, a question which would be asked in any other discipline
                                                      is where the frontier models fall short. We introduce GenOlympiad, a bench-
                                                      mark which provides the most challenging text prompts from nine capability axes
                                                      for stress-testing frontier text-to-image models. The assessed capabilities include
                                                      generating large quantities, performing deep reasoning, ensuring hard physical
                                                      consistency, following complex rules and so on. The prompts are designed such
                                                      that prompt alignment is visually verifiable (e.g., counting) instead of relying on
                                                      subjectiveness (e.g., style). Based on this, we develop an automated evaluation
                                                      framework which decomposes the prompt into easy and hard questions, and for
                                                      most hard questions, draws help lines to ground evidence for accurate grading.
                                                      We evaluate 20+ strong text-to-image models, including Nano Banana Pro, GPT-
                                                      Image-2.5, Seedream-5.0 and so on. We report that even the best-performing T2I
                                                      model (Nano Banana Pro) only achieves a strict score of 23.9 out of 100 and that
                                                      coding models such as GPT-6 Astra have higher prompt alignment scores (but not
                                                      as visually pleasing). We also derive insights in model evolution, alignment with
                                                      Elo scores, and effectiveness of our grounding-based evaluation protocol.

                                         1       I NTRODUCTION
                                         In artificial intelligence, benchmarks are introduced to expose frontier models to their capability
                                         boundaries, measure them, and seek solutions from the community. Some well known examples in-
                                         clude ObjectNet (Barbu et al., 2019) for vision model generalization, Humanity’s Last Exam (Center
                                         for AI Safety et al., 2026) for LLM question answering across subjects, SWE-bench (Jimenez et al.,
                                         2024) for automatic issue resolution, ARC-AGI benchmarks (Chollet, 2019; Chollet et al., 2025) for
                                         general intelligence, and FrontierMath (Glazer et al., 2024) for testing AI on advanced mathematics.
                                         Frontier text-to-image models can now produce high quality images (Sani et al., 2026; Li et al.,
                                         2026). This is evidenced by both real user scoring, where platforms like Artificial Analysis Arena
                                         rank models by asking users to compare image pairs head-to-head, and strong scores on automatic
                                         benchmarks. GenEval (Ghosh et al., 2023) has risen from 0.61 when first introduced in 2023 to
                                         ∼0.90 for recent models. PRISM-Bench(Fang et al., 2026) score which measures image-text align-
                                         ment and aesthetics is now over 85 by Nano Banana. However, these evaluation platforms either do
                                         not diagnose limitations of models (e.g., AA Arena) or see scores being saturated (e.g., GenEval)
                                         and thus no longer sit at capability boundaries. Therefore, we ask the question: when generated
                                         images already look high-quality, where do frontier image models still fail?
                                         We introduce GenOlympiad, an exam of 801 hardest prompts for frontier model evaluation, co-
                                         designed by AI and human. The prompts span nine capability axes, including quantity and precision,
                                         latent computation, physical consistency, spatial and 3D reasoning. To be hard, instead of adding
                                         more objects or textual conditions, the GenOlympiad prompts focus on hard constraints that must
                                         be strictly satisfied. An example prompt is ‘a compass on a boat, with its needle pointing toward the

Given each GenOlympiad prompt and an image generated by a frontier model, we design an auto-
matic pipeline to score the generations, which focuses on constraint satisfaction instead of general
alignment. Specifically, we do not ask the vision language model (VLM) ‘are there eight blue caps’,
because the answer can often be wrong. Instead, we break it down to atomic tasks, e.g., detecting
all the blue caps, drawing the bounding boxes on the image, and asking whether each bounding box
contains a blue cap. Evaluation becomes more accurate and interpretable if we let the VLM perform
such simple evidence extraction tasks and ground the task results (drawing bounding boxes and help
lines). Our scoring function is deterministic, matching the extracted evidence (e.g., bounding boxes
height, width, and coordinates) against the prompt. In addition, when grounding fails, we withhold
the task instead of assigning an unreliable score.
We evaluate a suite of frontier models on GenOlympiad with our evaluation protocols. We report
strict score which requires all constraints in a task to be correct, and relaxed score which gives a
partial score for some constraints. Detailed definition is in Section 3.3. Nano Banana Pro gains 23.9
in strict score and 40.0 in relaxed score out of 100, ranking first among T2I models, while the latest
GPT-Image-2.5-sunburst ranks second at 14.9 in strict score and 29.6 in relaxed score. We also find
that frontier closed models, e.g., the GPT-Image family, exhibit better GenOlympiad scores with

2     R ELATED WORK

Benchmarks for text-to-image generation. Some popular benchmarks focus on object presence
and attributes like color, relations or counting of a few objects (Ghosh et al., 2023; Kamath et al.,
2025; Paiss et al., 2023; Ye et al., 2025; Huang et al., 2025). Others focus on creative images that
rarely appear in the training set (Wu et al., 2024) or long prompt following, such as DPG-Bench (Hu
et al., 2024) and TIIF-Bench (Wei et al., 2025). Recently, more challenging benchmarks are intro-
duced by adding reasoning, e.g., Einstein’s favorite instrument (Li et al., 2024; Chen et al., 2025; Sun
et al., 2026; Niu et al., 2025; Singh & Zheng, 2023; Chang et al., 2025). Tasks in GenExam (Wang
et al., 2025) reflect various disciplines such as history, music, and biology, while MathGen (Liu et al.,
2026) focuses on mathematics content, e.g., angles, function, set and counting tasks with many ob-
jects. Prompts in Qwen-Image-Bench (Li et al., 2026) and ImagenWorld (Sani et al., 2026) instead
reflect real design demand in games, products, fashion, etc. Earlier benchmarks like GenEval have
already been saturated to 90%. Frontier models also made rapid improvement on recent benchmark,
e.g., GenExam reports a 74.6% strict score for GPT-Image-2; while MathGen report 53.7% pass
rate (similar to strict score) for Nano Banana Pro. In comparison, GenOlympiad curates the hardest
prompts and only sees 23.9% and 14.9% of Nano Banana Pro and GPT-Image-2.5 Sunburst.

Evaluation of generated images. Early metrics like Inception Score (IS) (Salimans et al., 2016)
and Fréchet Inception Distance (FID) (Heusel et al., 2017) measure how realistic images are. Later
metrics focus more on image-text alignment. CLIPScore (Hessel et al., 2021) calculates the simi-
larity between prompt and image, which is not strongly correlated with human judgement (Ghosh
et al., 2023). Human based metrics like Elo in Artificial Analysis Image Arena was later adopted,
but such metrics are too expensive to use and do not diagnose limitations of models. VQA-based
automatic metrics mitigate these problems (Hu et al., 2023; Cho et al., 2024; Lin et al., 2024) by
directly applying VQA models to image-question pairs. Other evaluation methods use vision tools
to obtain important evidence about texts or objects, e.g., GenEval (Ghosh et al., 2023) uses detec-
tion models; MathGen (Liu et al., 2026) uses OCR, contour detection, etc to extract text, angles,
etc. GenOlympiad is similar to GenExam/TIFA/DA-Score in breaking the prompt into questions,
but is different in using visual grounding in evaluation. GenOlympiad also shares similarity with
GenEval/MathGen and thinking with images (Yang et al., 2025) in using vision tool for evidence
collection; our key difference is using an iterative process to improve grounding (Table 2).

3.1   W HAT COMPOSES A TASK ?

Each GenOlympiad task contains a natural-language prompt and a bespoke evaluation program,
both of which are provided during evaluation. A prompt describes the image to be generated. Each
prompt has at least one aspect which is very hard to generate, e.g., 35 objects. The brainstorming of
the 801 prompts was performed by the authors with the help of AI, details is in Appendix A.3.
The evaluation program includes easy questions and hard questions. It also includes the pipelines
for evidence grounding and scoring (Section 3.3). The program is created by Claude Opus 5 with
human instructions (for details see Appendix A.3). As shown in Fig. 2, easy questions look like ‘are
there many dice in this photo?’ and ‘are the top faces of the dice clearly visible?’ Example hard
questions can be ‘Do these dice sum up to 131?’ and ‘How many dice in this picture?’

3.2     W HAT DOES G EN O LYMPIAD CONSIST OF ?

The 801 tasks in GenOlympiad overall evaluate nine capability axes below (topic distribution in
Fig. 3). More example prompts and success/failure images are shown in Appendix Fig. 1 and Fig. 17.

• Quantity and precision: to generate a large number of objects, exact ratio between objects, precise
  angles, and precise readings of instrument like ruler.
• Latent computation: computation outcome does not appear in the prompt, requiring the system to
  analyze the state for generation, e.g., 23 dice which sum up to 131.
• Physical consistency: to follow real-world physical constraints like gravity, optics, and stress, e.g.,
  water jets from different heights land at different ground locations.
• Spatial and 3D reasoning: examine the correctness of perspective relations and the expand diagram
  of 3D objects, e.g., a picture should be drawn in 3-point perspective.
• Text fidelity: readable text with constraints like font size and language habits like inverted question
  mark in Spanish, e.g., a paper printed with 12 lines of rhyme, each line ending with -ation.
• Symbolic systems: follow symbols in circuit, molecular graph, music sheet, etc, e.g., draw
  ClCCC1CCC(CC(=O)C2CCC(C(C)CC)C2)CC1 as a line-angle (skeletal) structural formula.
• Long-range consistency: parts of an image, even parts far apart, should be consistent, e.g., consis-
  tency of character in hats, clothes and rings in a multi-panel comic.
• Counterfactual instruction following: prompt is opposite to commonsense knowledge, e.g., a foot-
  ball team that gets the lowest score celebrate for its loss.
• World-knowledge grounding: to follow commonsense knowledge e.g., flags of countries; real-
  time information e.g., current air quality; The time difference between two specific countries
  should be correct.

3.3     E VALUATION FRAMEWORK

We design an automatic pipeline, which runs the evaluation program defined in Section 3.1, to grade
how well a generated image follows the prompt.
Easy questions easily asked. We use a TIFA-style method for easy question evaluation: the judge
VLM takes the easy question and the generated image as input and answers yes or no. Asking once is
enough, since the agreement with human answers is 94.7%, and majority voting over 3 independent
queries only slightly improves it to 95.3% at extra cost. As shown in Fig. 2, only after all easy
questions have been passed will we proceed with the hard questions; otherwise, we directly mark 0.
Grounding visual evidence for hard questions. 557 out of 801 tasks in GenOlympiad require
evidence grounding. Depending on questions, we draw different helping lines on the generated
image. As shown in Fig. 4, for counting questions, we aim to draw bounding boxes of objects of
interest; for the compass-sun question, we aim to draw an extension line of the compass pointer and
contour of the sun. There is no guarantee that grounding is successful at the first try, so after each try,
we ask the VLM whether grounding is successful, such as ‘does the blue line correctly overlay with
the compass pointer?’ If successful, then grounding is complete; if not successful, we repeat the
grounding step until reaching maximum trial times. The grounded evidence, e.g., bounding boxes
and lines, is then processed by a deterministic program. The program performs bespoke operations,
such as counting bounding boxes, calculating the sum of dice or checking whether the compass-
pointer line intersects the contour of the sun, to determine whether the hard question is satisfied.
Deterministic scoring. After each hard question has been verified, the scoring method will count
the number of hard questions that are successfully reflected in the generated image. For example,
there are two hard questions for Fig. 5: (1) is the number of dice 23; (2) do these dice sum up to
131? Following GenExam (Wang et al., 2025), we report two scores. In our ‘strict’ scoring, only
when all the hard questions are successfully passed will we give a mark of 100. In the ‘relaxed’

setting, different hard questions have different weights, and the weight sum of the successful ones is
the final score. The strict score is the percentage of the scored tasks that pass all the hard questions.
Grounding failure. If grounding is unsuccessful after the maximum number of trials, we remove the
task rather than force the grader to produce a potentially unreliable score. The failure scenarios may
be: an object is too small; object color is very close to the background; many objects overlay each
other and can not be clearly located. Grounding may also fail if a rendered text is not recognizable or
the generated objects do not match the objects expected by the evaluation program. We rank models
according to their grounding failure rate in Fig. 6.

4     E XPERIMENTS
We perform extensive evaluation and insight analysis of frontier image models on GenOlympiad. In
particular, we investigate the following research questions.

• What do comprehensive benchmarking results look like (Section 4.2, Table 1, Fig. 6)? Do frontier
  models have improved GenOlympiad scores over releases? (Section 4.3, Fig. 7, Appendix Fig. 13)
• What is the correlation of GenOlympiad scores with human ratings on Elo Arenas? (Section 4.3,
  Fig. 8, and Appendix Fig. 14, 15)
• How strongly does GenOlympiad evaluation results agree with human ratings? (Section 4.4, Ta-
  ble 2, and Appendix Tables 6, 4)

4.1   E XPERIMENTAL SETUP

We benchmark the following T2I models: GPT-Image 1, 1.5, 2, and 2.5 Sunburst (OpenAI, 2025b;c;
2026c;d); Nano Banana, Nano Banana Pro, and Nano Banana 2 (Google, 2025a;b; 2026); Seedream
4.5 and 5.0 Pro (ByteDance Seed, 2025; 2026); FLUX.2 Pro, dev, and Klein (Black Forest Labs,
2025); FLUX.1 dev and Schnell (Black Forest Labs, 2024); Stable Diffusion 3.5 (Esser et al., 2024;
Stability AI, 2024); SANA (Xie et al., 2025); and Qwen-Image-20B (Wu et al., 2025).
We evaluate open-weight models ranging from 0.6B to 20B parameters on the same server with a
single NVIDIA A100 80GB GPU. For each model family, we configure the context length of the
primary text-conditioning encoder to make the full prompt visible whenever possible. If prompt
length exceeds the context length, it will neither generate nor be calculated into the overall score.
We also benchmark two coding models, i.e., GPT-6 Astra (OpenAI, 2026b), GPT-5.6 Sol (OpenAI,
2026a) in medium effort with internet accessibility. We insert a system prompt (See Appendix A.4)
to let the coding models write a single HTML document. The content on this document is rendered
programmatically by JavaScript. We evaluate image aesthetics using the same method and setup as
PRISM-Bench (Fang et al., 2026), where the evaluator is GPT-4.1 (OpenAI, 2025a).
Prompt engineering (PE), which preserves the original constraints while improving T2I perfor-
mance, is evaluated on GPT-Image-2.5. We use PromptEnhancer-32B (Wang et al., 2026) and
GPT-5.6 Sol. For GPT-5.6 Sol, we use a fixed prompt from Tailored Visions (Chen et al., 2024).

4.2   B ENCHMARKING RESULTS

Comparing closed-source T2I models. As shown in Table 1, Nano Banana Pro obtained 40.0
relaxed score and 23.9 strict score and performs the best in text fidelity, counterfactual instruction
following, symbolic systems and so on. GPT-Image-2.5 is on par with Seedream 5.0 Pro and Nano
Banana 2. In addition, Seedream 5.0 Pro in latent computation and physical consistency performs
better than all the GPT-Image series.
Prompt engineering (PE) analysis. We test whether prompt rewriting is useful for GenOlympiad.
We use GPT-Image-2.5 as the base model. We compare PromptEnhancer-32B and GPT-5.6 Sol for
prompt rewriting while keeping the image model and evaluator unchanged. Results are shown in
Table 1. PromptEnhancer-32B brings nearly no overall improvement over GPT-Image-2.5, while
GPT-5.6 Sol increases the strict score and relaxed score from 14.9 to 33.0 and from 29.6 to 48.9,
respectively. The gain is significant in latent computation and text fidelity and very limited in spatial
and 3D reasoning. This demonstrates the usefulness of PE in T2I system design.

4.3       F URTHER A NALYSIS AND I NSIGHTS

Comparing grounding failure rates across models. As discussed in Section 3.3, grounding fail-
ures happen when some generated content cannot be grounded by Gemini 2.5 Flash. This does not
always mean bad generation: occluded objects may cause failure but may not be bad. In Fig. 6, we
compare the 25 models of their grounding failures and find that their ranking highly correlates with
their GenOlympiad scores (strict) with a Spearman coefficient of -0.92. It suggests that a stronger
model also tends to produce more easily grounded objects, which could be a result of post-training.
Do frontier models improve on GenOlympiad across releases? We evaluate different releases
of frontier models e.g., GPT-Image series, Seedream series, Nano Banana series. Fig. 7 visualizes
Table 1 as radar charts.. Later releases generally achieve higher scores, but the improvements are
highly uneven across axes. Some capabilities, such as text, spatial reasoning, and latent computation,
improve substantially, while others, such as world knowledge, show much slower progress.
Correlation of GenOlympiad scores with human-based arena scores. We also analyze the cor-
relation between GenOlympiad scores with human-based arena scores. The latter includes Image
Arena, LMArena and Design Arena. Correlation results are shown in Fig. 8. Although not intended,
we observe strong correlation between GenOlympiad score and the arena scores. In other words,
models that human prefers often obtain higher scores on GenOlympiad. On the other hand, outliers
do exist. For example, Nano Banana Pro has much higher GenOlympiad score but only ranks in the
middle of the three arenas. It indicates that differences exist between GenOlympiad and arenas.

   5                    C ONCLUSION

  We introduce GenOlympiad, a challenging set of generation tasks covering nine capability axes to
  find where frontier T2I models fail. Each prompt has an evaluation program of easy and hard ques-
  tions with 2.2 hard questions on average. We propose a grounding method for such hard question,
  where we draw helping lines on the image in an iterative way. We show that this method improves
  agreement with human judgments.We benchmark many strong models including open-source and
  close-source T2I models and show that the best T2I model, Nano Banana Pro, only has a strict score
  of 23.9. While coding models have higher strict score of 40.5, they suffer from poorer aesthetics.
  We also derive interesting insights, e.g., how a model family improves with their newer releases,
  prompt enhancer is useful, and GenOlympiad scores strongly correlate with human Elo scores.
  Limitation. GenOlympiad focuses on prompts that current frontier models find difficult, so the
  scores do not represent their performance on easy prompts. Moreover, GenOlympiad offers limited
  signal for non-frontier T2I models. Some prompts in GenOlympiad are too long to fit into the
  context of open-weight models, so for some open-source models, around 20 tasks do not have image
  generated or scored.Some scores are also withheld because the VLM judge does not correctly ground
  evidence. Finally, our evaluation is cost more requiring 59.5 VLM reads per image on average.

In this work, we used generative AI tools to assist with generating synthetic benchmark tasks, devel-
oping the conceptual framework of the nine capability axes, designing and providing feedback on
experiments, cleaning and reformatting the benchmark dataset, implementing evaluation programs,
translating and summarizing prompts used while constructing the benchmark, as described in Ap-
pendix A.4, evaluating generated images as part of the scoring pipeline, and providing preliminary
interpretation of intermediate experimental results. We have not used generative AI tools for any
other tasks with required disclosure, and tasks involving formulating mathematical claims, provid-
ing critical ingredients for proving mathematical claims, assisting in the writing of proofs, proposing
or refining hypotheses, and supporting qualitative and thematic data analysis are not applicable to
this work. Additionally, we used generative AI tools for brainstorming, sourcing and searching for
information, summarizing and analyzing existing literature. AI-assisted benchmark tasks and evalu-
ation programs were checked through manual spot checks and additional AI-based verification. The
evaluation pipeline was separately validated against human annotations as described in the paper.
We take responsibility for the final content of this work, including text, claims or artifacts produced
with the aid of generative AI.

 unavoidable to have some tasks that requires quantitative precision e.g., there should be 12 lines of

 be seen in Fig. 11. Most pairs of axes have low correlation, while several pairs even show negative

 The method we use to draw the correlation matrix. We take a classic statistics method called
 partial correlation to calculate the correlation between each axis. We do not directly compare the
 scores of two axes, because stronger models usually get higher scores on many axes at the same
 time. So we take methods to mitigate the bias from models’ capability by using linear regression.
 For each axis, we first predict what score a model should get based on its overall performance using
 linear regression shown in Fig. 10. We then compare whether the model performs better or worse
 than this expected score on different axes. For example, if models that perform better than expected
 on latent computation can perform either better or worse than expected on physical consistency,
 then these two axes have a low spearman correlation.

  model receiving a score of 0. This keeps tasks that some models can solve but others fail, so our
  benchmark can better distinguish different models.

frontier models from different model families, instead of using only one model or several models
from the same family.

A.4   P ROMPT T EMPLATES

This section gives the prompts used in this paper, all prompts in abridged. We first give the few-shot
examples that we wrote by hand before building the benchmark. We then give the instructions of
the agents in the task generation protocol of Appendix A.3. We evaluate coding models by giving
system prompt. Some of them were written in Chinese and are translated here. All these following
prompts are summarized and translated by Claude Fable 5.1.

Positive examples. Each prompt below looks ordinary, but frontier T2I models fail it for a reason
that can be named. Where we recorded the outcome of our first trials, it is given after the prompt.

1. Exact geometry of a technical drawing.
           Generate a precise 2D CAD-style engineering drawing in strict orthographic front view of a
           flat mechanical panel. Visual style: - pure white background - thin black uniform lines - no
           perspective - no shading - no textures - no shadows - no color - no text - no dimension annotations
           - geometry only - crisp technical drawing appearance Geometry: 1. Outer boundary: a rectangle
           of width 300 units and height 200 units. 2. At the geometric center of the rectangle, draw
           two concentric circles: - outer circle diameter 60 units - inner circle diameter 30 units 3. Draw
           four identical circular holes of diameter 16 units, centered at: - (60, 150) - (240, 150) - (60,

From these trials we drew two lessons for the agent. First, a task is weak if its final picture can be
described in words, because an agent can compute the result and rewrite the prompt into a simple
description. Second, a task is weak if a language model can simplify the prompt, for example by
dropping an object that the prompt asks for but that must not be visible.

Abridged instructions of the agents. Each role in the protocol is played by a separate agent that
works from a written instruction. The lists below are abridged translations of these instructions.


Instruction to the brainstorming agent (abridged, translated from the original)

  1. Start from a real scene, such as a work station, a home, a street, a sport, a game or a document. Do not
     look for a scene to dress up a mechanism you already like.
  2. Inside the scene, find a hard constraint that a person who does this work would notice at a glance if it
     were drawn wrong. Only then ask whether it is difficult.
  3. Say in one sentence who would need this picture and what they would do with it. This field is required.
  4. Ask whether this picture existed in the world before we set the task. If not, the mechanism may still be
     good, but the carrier is a teaching prop: attach a real-life carrier and change nothing else.
  5. A task must satisfy four things at once: it is a real commission; a layman can tell right from wrong in one
     look; the answer appears nowhere in the prompt; and judging it leaves behind a picture worth showing.
  6. Tell your candidate in one sentence: what the viewer sees, where the mistake shows, and why this picture
     really exists. If you cannot, drop it.
  7. Take the difficulty from what actually breaks models: withhold the key number; make a quantity travel
     from one place of the picture to another; make each cell depend on other cells; ask for a composite
     transform to be inverted; leave one step outside the rule table; give no scale at all.
  8. Avoid what never breaks models: writing out the whole rule table for the model to follow; describing the
     final appearance; asking whether something appears anywhere in the image; exact counting on a regular
     layout.



                                                         27
Preprint




  9. Difficulty must come from the process, not the dose. More objects, more rows, more decimal places and
     more arithmetic are a ladder, not a new task.
 10. To make a task harder, use a richer real specification or a real convention of the trade, or move the check
     to after the thing has been assembled. The amount of data stays the same.
 11. One conversion, one addition or one comparison is allowed on any axis. Multi-step arithmetic belongs to
     the latent computation axis and may not be disguised.
 12. Test the candidate three times. Hand the withheld number to the model for free: if the task becomes easy,
     it tests arithmetic. Reduce the count to five: if it becomes easy, it tests counting. Make the unusual rule
     normal again: if it is still hard, the difficulty is not where you said it was.
 13. One task per mechanism. Two candidates are the same task if their failure conditions are the same
     sentence, whatever the objects are. Check for collisions across all nine capability axes, not only your
     own.
 14. Do not clone the worked examples. Learn the formula, not the picture.
 15. Before a candidate is released, name the nearest task that has already been scored, give its score, and say
     which specific quantity this candidate keeps outside the prompt. ‘It is harder’ is not an answer.
 16. Declare anything you truncated, sampled or relaxed. You do not approve your own candidate: a reviewer
     does.




Instruction to the task-writing agent (abridged, translated from the original)

  1. Write the failure condition and the evaluation program before you write the prompt.
  2. The prompt is a work order, not a construction drawing. It has four parts: the scene and the deliverable;
     the material that fixes the inputs; the purpose; and the constraints, including what must not appear. Never
     teach the model how to draw, and never state the answer.
  3. Fix the input, not the output. Whatever the model should have before it starts may be given exactly.
     Whatever it should only produce after working may not appear.
  4. List every element of the expected answer and confirm that at least one cannot be found word for word
     in the prompt.
  5. A full rule table may be given, but after the table there must still be one step of computation, placement
     or conservation that cannot be looked up in it.
  6. Do not lay the picture out element by element with a string of imperatives. That turns the model into a
     typesetter and measures nothing. Do not write down the final appearance.
  7. The expected answer must promise something, and it must contain numbers.
  8. A real industrial setting is not enough by itself. Its value is the part of the real specification that cannot fit
     in the prompt. Say which part that is.
  9. For a task about orientation or visibility, fix the orientation with a natural anchor in the scene, such as a
     person reading the face of the object. Never state the camera-side conclusion, and never stay silent about
     orientation.
 10. Rotate your own reference image by thirty degrees and score it again. If the score flips, the orientation
     was not fixed hard enough. State the sign convention wherever one shape could be read as two different
     signs.
 11. If the VLM could answer the question from its own knowledge without looking at the image, the candi-
     date is rejected. No rewording rescues it.
 12. Answer two questions in writing. How could a model that knows nothing guess a score? How could a
     strong model get around the ability itself? Close both routes.
 13. Require a result that cannot be faked by drawing, such as specific numbers or a correctly placed object.
     Do not ask whether something appears anywhere in the image.
 14. No exact counting on a structured layout such as a table or a calendar. Counting tasks must scatter their
     objects.
 15. Across the difficulty levels of one task, change at least two of carrier, setting, composition and style.
     Changing only the numbers is not enough. Re-skinning counts only if it changes the mechanism: counting
     apples and counting pears is one task, not two.
 16. The picture that the prompt describes must have existed in the world before the task was set.




Instruction to the evaluation-program agent (abridged, translated from the original)


                                                         28
Preprint




  1. Perception belongs to the VLM and arithmetic belongs to code. The VLM never does arithmetic. Where
     the answer needs a computation, the VLM only reports what it sees in a machine-readable form, and a
     program computes the conclusion.
  2. Every step must leave an overlay on the image that marks the element this step looked at.
  3. Ask the VLM one observable fact at a time. Every ‘and’ belongs in code. Split a compound question into
     separate questions and combine them in code.
  4. Every question must be answerable in seconds by a person with no background who is shown the crop.
     Move all domain knowledge into code. Only two kinds of question may need expertise: transcribing a
     notation, and marking geometry.
  5. One question, one fact. No comparisons that are hard to follow, no double negatives, and no examples,
     because an example becomes the VLM’s target list. Fix the answer format.
  6. Keep the phrase that names what to locate short. A long phrase breaks the check itself, and the symptom
     is a refusal to read, not a wrong number.
  7. A question may never contain a correctness word, state an expectation, or reveal the shape of the expected
     answer. Never give the expected count to the step that proposes the boxes. The count is the answer.
  8. Do not add a scene-level easy question by default. Only a real precondition earns one, because a scene
     check tends to reject the most correctly drawn images of an unusual task.
  9. If the expected answer fixes the geometry, draw it over the image and ask whether it coincides. If the
     criterion is a geometric relation, draw the construction so that the conclusion is visible on the image.
 10. A count that decides the score must go through the loop: locate, confirm, read, compute. The scored
     count is the number of items confirmed one by one, never the number of boxes proposed. Counts of at
     most ten are exempt.
 11. Use only the allowed operators. A new operator needs a task-neutral design and at least three tasks that
     will reuse it.
 12. Complexity is a defect. A task that no allowed operator can evaluate is better removed than kept.
 13. There are three outcomes, never two: a scored result; a zero caused by the model’s own broken image;
     and a failure of the evaluator. A failure of the evaluator, or a refusal by the VLM, withholds the task and
     is never scored as zero.
 14. Every zero must name the fact that was violated. That fact must be drawn on the image, and it must have

           You draw pictures by writing code.
           The user message is a picture description. Write one self-contained HTML document that
           draws that picture, and return nothing else.
           Looking Things Up.
           • You have a web search tool. Use it whenever the description depends on a fact you
             would otherwise be guessing at: a live or dated figure, the real appearance, markings,
             proportions or specification of an actual object, place, instrument or document. Search
             first, then draw what you found.
           • Search is yours to judge. A picture that needs no outside fact needs no search.
           • What you bring back from a search must end up in the code you write. The rendered
             page itself has no network: it cannot load a photograph, a font, a map tile or a data file
             from anywhere, so a fact is only useful once you have turned it into drawing instructions.
             Pasting a picture from the web would be collecting, not drawing, and the page cannot do
             it anyway.
           Canvas.
           • The drawing surface is exactly {W} pixels wide and {H} pixels high. Fill it. Do not
             leave a border of blank page around the picture and do not draw outside it.
           • Use either a <canvas> element of exactly {W}x{H} with an inline <script> that draws
             on its 2D context, or one inline <svg> element of exactly {W}x{H}. Either is fine.
             Mixing them is fine.
           • Give the page a background. A transparent or default-white page counts as an undrawn
             picture.

           Self-Contained, No Network.
           • Everything is inline in the one document. No <img src>, no <link>, no external <script
             src>, no fetch, no XMLHttpRequest, no WebSocket, no import from a URL, no @font-
             face pointing at a file, no web font service. Nothing is downloaded: the page is rendered
             with the network off, so anything external simply will not arrive.
           • Text must use fonts already on a normal machine. Name generic families such as sans-
             serif, serif, monospace, or common system faces with a generic fallback.
           • No alert, confirm or prompt. No window.open. No timers that keep changing the picture:
             draw the finished picture, do not animate it.
           When The Picture Is Finished.
           • Draw on load, synchronously if you can.
           • The moment the drawing is complete, set window. done = true. A screenshot is taken
             as soon as that flag appears, so setting it early gives you a half-drawn picture and never
             setting it costs you nothing but a wait.
           • The document must not throw. An uncaught exception is a blank page and scores nothing.
           What You Are Being Asked For.
           • Draw everything the description asks for, with the counts, the positions, the text, the
             relations and the values it names. Every quantity in the description is checkable in the
             picture afterwards, so compute it in code rather than eyeballing it: lay out with arithmetic,
             place things by coordinates you work out, and write the labels the description dictates,
             spelled exactly as it spells them.
           • You get one attempt and you never see the rendered result, so prefer constructions you
             can be sure of over constructions that need tuning by eye.
           • Make it look like the thing described, not like a diagram of the thing, unless a diagram is
             what was described.
           Output Format.
           • Reply with exactly one fenced code block, opened with three backticks and the word
             html, and nothing before or after it. No explanation, no notes, no second block.
